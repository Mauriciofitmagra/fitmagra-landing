# Wompi Colombia: documentation map and integration findings

Collected 2026-10-28 from the official Wompi documentation sitemap. The 67 linked Colombia pages cover incoming payments, payment-method APIs, plugins and payouts. Pages were downloaded for review; the integration findings below focus on FitMagra's incoming payments, not every unrelated product. Documentation and provider behavior can change; recheck before production.

## Findings for FitMagra

- Wompi Web Checkout is a hosted, one-time payment flow. Generate a unique reference and calculate the integrity hash on the server; the amount is in COP cents. The browser return is informational and must not settle a payment. [Checkout](https://docs.wompi.co/docs/colombia/widget-checkout-web/)
- Verify event checksums from the actual ordered property list and the event secret. The published example signs transaction ID, status and amount, but not reference or currency. Therefore, do not trust unsigned webhook fields to decide whose payment to credit: use the verified transaction ID to fetch authoritative transaction details server-side, then match the saved reference, amount, currency, environment and merchant before an atomic settlement. This matching requirement is an inference from the documented signature coverage. [Events](https://docs.wompi.co/docs/colombia/eventos/), [transactions](https://docs.wompi.co/docs/colombia/transacciones/)
- A payment retry can create another transaction ID with the same reference. Idempotency must prevent double credit by both transaction ID and the saved purchase reference; a declined attempt must not prevent a later successful retry. [Payment retries](https://docs.wompi.co/docs/colombia/reintento-de-pago/)
- The current billing event code explicitly allows concurrent events for one member to overwrite each other. Resolve that race and exercise duplicate, out-of-order, concurrent, altered and retried events before enabling real checkout. Continue to honor admin-invited access without requiring payment unless Roberto changes that rule.
- Wompi uses distinct sandbox and production public, private, event and integrity keys. The current transactions page says transaction lookups require a private key on the server; no secret belongs in client code or logs. [Environments and keys](https://docs.wompi.co/docs/colombia/ambientes-y-llaves/), [transactions](https://docs.wompi.co/docs/colombia/transacciones/)
- Roberto chose automatic recurring charges. They require a different payment-source/API integration, the member's explicit recurring-charge authorization and both Wompi policy acceptances. The acceptance-token guide says the legacy merchant endpoint is due for retirement on 2026-10-31; use the current endpoint for direct API collection. [Payment sources](https://docs.wompi.co/docs/colombia/fuentes-de-pago/), [acceptance tokens](https://docs.wompi.co/docs/colombia/tokens-de-aceptacion/)
- Sandbox credentials and test cases are needed to test approval, decline, pending, retries and event handling end to end. The Supabase port, legal review and launch checks remain prerequisites. [Sandbox data](https://docs.wompi.co/docs/colombia/datos-de-prueba-en-sandbox/)
