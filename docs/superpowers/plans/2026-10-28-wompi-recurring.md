# Wompi recurring payments

Roberto selected automatic recurring charges. FitMagra continues to allow admin-invited members access independent of payment. Keep billing unavailable until the full flow is tested with a Wompi sandbox account and the launch gates are met.

## Implementation sequence

1. Complete the Supabase database port and verify a server-only database role, connection isolation, transaction rollback, and concurrent access. Do not run a billing scheduler on the SQLite-era stand-in code or a shared unverified connection.
2. In the member area, present the plan, amount in COP, billing period, first and subsequent charge dates, renewal and cancellation terms before collecting explicit consent for recurring charges. Obtain and present both current Wompi policy links and require their separate acceptances. Never record card numbers or security codes in FitMagra. Preserve consent evidence and account for the member's right to cancel future charges.
3. Build Wompi payment-source setup using the provider's tokenization flow and sandbox credentials. Handle pending, failed and customer-authentication steps, including 3DS when enabled. Only offer methods confirmed for the merchant and the chosen recurring flow. Do not assume the hosted one-time checkout creates a reusable payment source.
4. Persist a charge intent before contacting Wompi: member, source, plan, price, period, unique reference, and explicit consent. Enforce a unique member/period intent in the database. Process due intents with a durable scheduler and an atomic claim; cancellation must prevent an unclaimed future intent from being charged. Treat cancellation racing with an already-submitted request as a separate, visible state.
5. Handle ambiguous API outcomes by reconciling the existing reference and provider transaction before issuing any new attempt; never infer a failed charge from a timeout. Distinguish a provider retry transaction from a new billing period. Ensure multiple workers, redelivery and restart cannot cause two successful credits or charges for the same period.
6. Verify Wompi's signed event fields in the supplied order. Retrieve authoritative transaction details server-side and match them to the stored intent, amount, currency, environment and merchant. A browser redirect is informational. Apply successful, declined, pending and reversed outcomes in an atomic, idempotent transaction; a delayed failure must not override a later success. Return an error for retryable failures so Wompi can redeliver.
7. Provide accessible ES/EN payment status, clear pending/error messages, payment-method management, cancellation, and receipts/history as supported. Confirm billing copy and policy with counsel and Mauricio. Ensure the mobile flow remains usable without relying on color alone.
8. Exercise sandbox approval, decline, pending, 3DS, retries, timeouts, duplicate and out-of-order webhooks, two concurrent scheduler workers, price changes, cancellation races and database failures. Verify that browser-side tampering, a different merchant and unsigned webhook fields cannot credit an account. Test real PostgreSQL multi-connection behavior as well as the Worker runtime.
9. Only after human review and sandbox sign-off, configure production credentials and event delivery through the approved operational process. Never commit credentials, emit payment details in logs, or change Cloudflare or Wompi settings as part of tests.

## Current blockers and provider details

- Wompi's [payment-source documentation](https://docs.wompi.co/docs/colombia/fuentes-de-pago/) describes tokenized automatic payments, while its [3RI guide](https://docs.wompi.co/docs/colombia/fuentes-de-pago-3ds/) says merchant activation and card-network support vary. Merchant eligibility is not yet confirmed.
- Wompi's [acceptance guide](https://docs.wompi.co/docs/colombia/tokens-de-aceptacion/) requires explicit acceptance of two current policies for direct API collection. The former merchant endpoint is scheduled for retirement on 2026-10-31.
- The existing manual-payment route writes its audit after settlement; a failed audit and retry could duplicate credit. It remains unreachable and must be redesigned or removed before being enabled.
- The Worker is not yet connected to PostgreSQL, and the current Supabase test setup does not prove behavior across independent real database sessions. Previously exposed Supabase credentials must be rotated before production.
- Legal review, retention implementation, R2 provisioning, browser visual QA and staging checks remain open. No production deploy is authorized by this plan.
